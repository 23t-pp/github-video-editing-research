# 对现有剪辑项目的判断：下一步该补什么

最有价值的增量是模板参数、语义选镜、统一时间线和独立质检。已有环境已经能检测音频节奏、生成镜头表、渲染卡点视频，无须把搜到的所有引擎重新安装一遍。

本节结合用户另一个窗口提供的只读核验交接，以及主流程对关键源码和两个成片文件的复核。公开记录使用项目别名，不包含本机绝对路径、素材、成片或私有项目源码。因原文件未公开，第三方不能仅凭本仓库在线复验这些本机观察；它们与有公开固定SHA的GitHub审查证据分开标记。

## 发现1：同一个时间线字段，不一定真的被渲染器执行

项目B的镜头配置有5个非1.0的speed值。主流程读取当前构建函数，看到它应用zoom、shake、drift和grade，但该函数没有读取speed，也没有生成对应setpts变速过滤器。

**可支持的结论：** 按当前这段构建实现，speed字段不会在这一步生效。

**不能直接推出：** 现有成片的全部速度必然错误。还需查输入片是否预变速、缓存片来源、具体构建版本，并运行最小样例。

对选模板的启发：不能只看JSON中是否存在“speed”“transition”“beat”字段；要追踪它是否进入最终渲染命令。这也是本次审查GitHub源码而不只抄README的原因。

## 发现2：帧数与秒数必须统一

```text
时长（秒） = 帧数 ÷ 每秒帧数
20秒 × 24fps = 480帧
实际479帧 ÷ 24fps = 19.958333秒
```

项目B存在1帧规格差；源码使用“每镜头时长分别四舍五入成帧数，再求和”。这可能造成累计误差，但本次没有逐段比对全部缓存片，不能把它写成已完全证明的唯一根因。

项目C已有更适合作为统一规范的做法：先把绝对起止时间分别量化为startFrame/endFrame，再用两者相减求镜头帧数。它避免了把每段时长单独取整再累计的一类误差，但仍需处理最后一帧、转场重叠和音频时长。

建议以后统一采用下列字段。以下是**建议格式示例**，不是声称某仓库原生支持的接口：

```json
{
  "fps": 30,
  "totalFrames": 900,
  "shots": [
    {
      "source": "clip-01.mp4",
      "sourceInSeconds": 2.4,
      "startFrame": 0,
      "endFrame": 60,
      "speed": 1.0,
      "role": "opening"
    }
  ]
}
```

这里endFrame约定为不包含的结束边界，所以0到60共有60帧。将单位写进字段名，比把秒、毫秒、帧都叫“time”更容易检查。

## 发现3：质检拼图没有覆盖全片

项目D当前抽帧脚本先用视频时长计算约每隔几秒的采样位置，随后又把这个秒数除以60传给FFmpeg的`-ss`。结果24个采样点只落在约0.05–1.017秒。

主流程直接核对了源码中的两步运算；支撑窗口还查看了现有拼图，确认标签和画面集中于开头。因此该拼图不能证明60.7秒全片视觉已检查。

适合新手的理解：FFmpeg的`-ss`接收秒。如果变量已经是秒，就不要再次当成帧除以fps。改进方案应先明确单位，再覆盖全片、首尾、转场和高潮；本次没有修改原项目脚本。

这个案例也说明：GitHub仓库里有一个叫`verify.py`或`test`的文件，不等于验证本身足够。要检查它到底在验证什么。

## 发现4：内部“贴拍误差为零”不是独立验收

项目C将镜头吸附到一份beat grid，再把镜头时间与同一份grid比较。这可以检查内部一致性；它不能单独证明编码后的MP4切点与音乐真实瞬态准确对齐。

后续独立验证应至少分别检查：计划时间线、编码后实际帧边界、音频瞬态与听感。真实beat检测也可能有半速/倍速、起拍偏移或稀疏段回退。

项目D有208个镜头，内部切换边界通常是207个；不要把“镜头数”和“刀数”当同一个数。

## 根据实际缺口挑新增项目

| 需要补的能力 | 优先研究对象 | 为什么有新增价值 |
|---|---|---|
| 可换素材的情绪混剪结构 | easyedit | 有speech→montage→hero编排和独立视觉模板 |
| 最小、易读的节拍剪辑流程 | beat-synced-edit | 音频分析、选段规划、EDL、渲染分别成文件，适合对照已有脚本学习 |
| 照片批量模板 | VVV / slideshow | 有参数入口和照片/音乐结构，减少每次重搭镜头 |
| 成套美术样式 | Opus30 / 官方HyperFrames launches | 具体可编辑成品，补审美结构与转场，不替代现有音频分析 |
| 可视化时间线与对话式改片 | OpenChatCut | 值得验证可编辑性与多步骤操作，但软件栈较大 |
| 根据画面语义找镜头 | agentic-video-editor 等视觉模型方案 | 与当前按运动/亮度/对比度分池的规则选镜不同；需测试模型费用与实际选段质量 |

建议先完成一个小实验：用同一批自有素材和同一段30秒音乐，对照已有流程与一个新增模板。比较修改次数、镜头复用、帧数、节拍误差和最终可编辑性。这个实验是下一阶段建议，本次未执行。
