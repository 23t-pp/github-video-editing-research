# 本次完整发布：实际做了什么，命令是什么意思

本次新发布57个附件，共21,650,704,440字节。工程Release有27个附件，JPG Release有30个附件。旧发布及原成果没有被替换。

## 1. 为什么不把206万张图片直接提交到Git

Git保存源码、清单和中文说明。大媒体放在GitHub Release附件中：每集一个`S1E01.tar.gz`至`S1E24.tar.gz`，外加恢复工具和校验清单。24档实际包含全部2,061,018个JPG路径，下载后能恢复原目录。

60Hz采样会多次指向同一个源帧。本次823,577个常规JPEG加1,237,441个硬链接条目，合计2,061,018个采样路径。硬链接保存对应关系而不反复存储同一份JPEG字节；不支持硬链接的目标盘由恢复工具自动复制字节。它没有生成额外动作帧。

## 2. 本地打包和审核

`pack_jpg.py`按集读取索引和样本清单。每个常规JPEG写入档案后，实际重新流读档案核对SHA-256；硬链接必须指向同一档内已出现的合法源路径。独立审核agent另用`audit_jpg_archive.py`重新检查全部24档，不采用打包方一句“完成”作为结论。

本地检查覆盖全部2,061,018条JPG路径、全部823,577个常规JPEG的字节SHA及全部硬链接映射。实际恢复测试覆盖第一集全部86,102个路径，并另查硬链接身份、复制模式和可复现的JPEG解码样本。其他23集验证的是全档案条目和字节图，并未声称逐集都实际展开到磁盘。

`finalize_jpg.py --wait`只在24份报告均通过、三个总数精确一致时生成`jpg-manifest.json`、`SHA256SUMS-JPG.txt`与`JPG-ARCHIVES.csv`。

## 3. 上传不是复制完就算成功

上传器对每个ready文件执行与以下等价的命令：

```powershell
gh release upload jjk-s1-jpg-60hz-2026-11-05 ./S1E01.tar.gz --repo 23t-pp/github-video-editing-research
```

`gh`是GitHub CLI；`release upload`上传附件；后面第一个参数是发布标签；`--repo`明确目标仓库。工程附件使用另一标签`editing-projects-2026-11-05`。

随后调用`gh api`读取GitHub返回的附件`size`、`digest`与`state`：必须同时满足大小相等、`sha256:`值相等、状态为`uploaded`才记为远端成功。本次57项全部匹配。失败请求有有界重试，同名但内容不同的已成功附件拒绝覆盖。

## 4. 保存源码并正式公开

本次先在`publish-all-20261105`分支提交5966份源码和文本镜像，再加入完整下载中枢与最终清单。文件实际复制SHA及Git暂存对象SHA均已核对。归档文本用`.gitattributes`关闭换行转换，以保留证据原字节。

关键实际命令：

```powershell
git -c core.longpaths=true fetch origin main
git -c core.longpaths=true merge-base --is-ancestor FETCH_HEAD HEAD
git -c core.longpaths=true push origin HEAD:refs/heads/main
```

`core.longpaths=true`允许Windows处理较深目录；`fetch`读取最新主分支；`merge-base --is-ancestor`检查远端历史是否包含在本地历史里；最后一条把当前提交正常推到主分支。没有使用强制推送。

正式发布的源码基准提交是`0cc7fe53487de5fe76f9337e9bc7ac65a57e7bc5`，两个Release标签均指向它。后续主分支追加的是公开验收报告和文档账本。

```powershell
python -X utf8 ./publish_releases.py --commit 0cc7fe53487de5fe76f9337e9bc7ac65a57e7bc5 --publish
```

这个命令在本次发布暂存目录中执行。脚本先要求封闭上传队列、57项远端成功、24集精确总数、独立审核通过、目标提交已在GitHub，再把两个草稿Release设为公开。`-X utf8`让Python使用UTF-8处理中文路径；不要用`-O`关闭脚本中的assert门禁。

## 5. 公开后还检查了什么

`verify_public_delivery.py`不带登录凭据访问两个Release、源码README和实际下载地址。它核对主分支及两个标签的源码基准，再比对首集、末集JPG归档及MP4的前64字节；小于2MiB的总清单和审计ZIP完整下载核SHA。独立审核另检查全部57个附件的公开API状态、大小和digest，并下载小附件核对SHA。

公开下载测试中，JSON小附件的Range请求曾返回504，重试后可访问；进一步改成小附件普通完整下载，避免这类网关Range问题。这个现象没有改变已上传文件的SHA。最终通过报告保留在`publication/evidence/independent/`。

## 6. 你在本机下载和恢复

在PowerShell中逐行执行：

```powershell
New-Item -ItemType Directory -Path D:/video-backup/packages -Force
gh release download editing-projects-2026-11-05 --repo 23t-pp/github-video-editing-research --dir D:/video-backup/packages
gh release download jjk-s1-jpg-60hz-2026-11-05 --repo 23t-pp/github-video-editing-research --dir D:/video-backup/packages
Set-Location D:/video-backup/packages
python -X utf8 ./restore_projects.py --downloads . --workspace D:/video-backup/workspace --with-sources
python -X utf8 ./restore_jpg.py . --destination D:/video-backup/workspace/outputs/jjk-s1-workflow/素材集_60Hz_JPG --manifest ./jpg-manifest.json
```

前两条下载命令分别取工程和图片库，`--dir`指定存放压缩包的位置。`Set-Location`切换当前目录；`.`表示当前目录。`restore_projects.py`恢复工程并回填单独发布的HF/OCC文件；`restore_jpg.py`恢复24集图片目录并校验内容。`--destination`停在素材库根目录，工具自己创建集号目录。恢复中断后按JPG工具说明使用`--resume`，原有文件会重新检查。

如果`python --version`找不到命令，本次电脑可把`python`替换为`& 'C:/Users/PC/.cache/codex-runtimes/codex-primary-runtime/dependencies/python/python.exe'`。完整用法以两个恢复工具的`--help`为准。
