# 工作流也要验收：本次发现的两个缺口

这份记录保留真实故障，避免把“写了监控脚本”当成“监控一直正常”。影片通过和工作流完整是两项验收。

## 1. 总监控被Windows文件占用中断

最终界面复查时，素材与渲染已完成，但总监控的旧心跳仍停在19:43:49。读取原会话的实际错误栈，确认`Path.replace()`遇到`PermissionError: [WinError 5]`后退出。渲染执行器自己的心跳、20段proof、源取片和全季校验报告另有完整记录；它们不由旧的总监控页面替代。

修复做了两层：

1. `monitor.py`使用带PID的临时文件，替换失败后最多重试6次，总退避约1.55秒。持续失败仍明确报错，不写“成功”的假心跳。
2. 学习服务独立用当前时间减去心跳时间。未封存时超过180秒，就显示旧状态告警；封存后监控按设计退出，不误判为故障。

实际故障注入验证调用生产函数：前两次替换失败、第三次成功；连续6次失败则抛错，旧已提交JSON保留。另验证181秒过期、180秒未过期、封存状态不误报。重启后真实API显示新心跳与四轮结果，记录见`workflow/monitor-repair/validation.json`。旧源码和差异也保留在该目录。

你可以这样检查，而不是只看网页里一个“完成”字样：

```powershell
$s1Root = 'D:/gpt/2026-11-04/ps-c-windows-system32-winget-install-2/outputs/jjk-s1-workflow'
$s1Py = 'C:/Users/PC/.cache/codex-runtimes/codex-primary-runtime/dependencies/python/python.exe'
& $s1Py -X utf8 "$s1Root/scripts/workflow.py" status
Invoke-RestMethod 'http://127.0.0.1:5351/api/status' |
  Select-Object time,monitorAgeSeconds,monitorStale,monitorSealed
```

## 2. 四轮结束后，next没有继续派工程验收

独审真实执行`workflow.py next`，发现四轮影片完成后返回空动作，但OCC、最终UI与总验收还没有齐。`seal`硬门能阻止提前交付，但“下一步”的调度链不完整。

整改把最后几步也加入真实文件驱动的分派：OCC官方回环→UI与媒体交付验证→独立最终验收→封存。文件不存在、媒体缺失、hash变化或只拿旧L3界面报告，都应给出明确待办，不能只凭文件名存在就放行。CLI只返回角色与动作，由编排代理实际调起对应代理，没有伪造模型调用。

修改前的空动作、源码、diff与验证放在`workflow/final-dispatch-repair/`。最终完整性以该目录验证、独立总验收和`workflow/delivered.json`为准。

## 为什么这值得学

多代理能并行工作，也会带来状态和版本问题。应让每一项“通过”都指向实际输入、输出、执行者和审核证据；同时检查监控本身是否还活着。达到四轮、出现输出文件或某个代理说“完成”，都不足以单独封存整个任务。
