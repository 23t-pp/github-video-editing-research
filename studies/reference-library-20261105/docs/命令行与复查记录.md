# 命令行处理流程：每一步做什么、留下什么证据

这是可复查的操作记录与复现方法。它解释目的、输入、输出、发现的问题和验证范围，不把未经验证的内部推测写成制作事实。命令示例在学习库根目录执行；具体媒体路径由本地清单提供。

## 第一步：确认素材，不用文件名猜内容

使用`ffprobe`读取视频流、音频流、尺寸、帧率、时长、色彩信息。使用SHA-256识别完全相同的文件。

```powershell
ffprobe -v error -show_streams -show_format -of json 'D:\素材\参考.mp4'
Get-FileHash -Algorithm SHA256 -LiteralPath 'D:\素材\参考.mp4'
```

- `-v error`只显示错误，避免一长串启动信息。
- `-show_streams`看视频/音频轨；`-show_format`看容器。
- `-of json`输出结构化结果，脚本可以准确读取数字。
- 哈希识别文件字节是否相同；两个不同转码不相同，不代表内容不同。

实际结果保存在`data/media-index.json`：20条短片共222,521,112字节，20个不同视频SHA-256。不要把容器时长当作最后一帧的时间，例如V17视频流为25.8秒，容器略长。

## 第二步：保留原帧，而不是把24帧复制成60帧

```powershell
ffprobe -v error -select_streams v:0 -show_entries frame=best_effort_timestamp_time,pict_type,key_frame -of json 'D:\素材\参考.mp4'
```

`v:0`表示第一条视频轨。PTS是画面真正应该显示的时间；对于可变帧率，不能用“帧号÷平均帧率”替代它。输出中的帧号从0开始，F0就是第一张。

本库实际运行`analyze-native-frames.mjs`，为所有20条视频生成：

```powershell
node .\scripts\analyze-native-frames.mjs .\manifest.local.json
# 只重做某条时，在最后追加稳定编号，例如 V05
node .\scripts\analyze-native-frames.mjs .\manifest.local.json V05
```

`manifest.local.json`是含ID、路径、fps、fpsValue、sha256的本机数组；可以用`prepare-manifest.mjs`根据路径配置生成。它不进入公开仓库。

内部解码采用`-fps_mode passthrough`，没有`fps=60`或光流插帧。每帧缩为96×54计算RGB差异、颜色直方图、亮度和相邻缩略图是否完全相同。图谱每页排10×6个原帧，并印出F号和PTS。每秒图谱只用于导航，不替代连续原帧图谱。

**核验：** 17,290个PTS记录、17,290行指标、17,290个有效图谱格一致；299页的首尾帧连续，无缺口。统计到的相邻相同缩略图是源文件内容的结果，不能称作程序补帧，也不能证明原尺寸帧完全一致。

### 遇到的本机问题：FFmpeg不能直接写文件

本机FFmpeg可以读取和编码，却无法直接落盘。处理方式是让FFmpeg把二进制结果写到`pipe:1`，由可写入的Node进程保存。没有改系统防护。

```js
// 展示核心模式，完整容错处理见实际脚本。
const child = spawn(ffmpeg, argsEndingWithPipe1, { windowsHide: true });
const chunks = [];
child.stdout.on('data', chunk => chunks.push(chunk));
// 等退出码确认成功后，再把Buffer写到目标文件。
```

不要在旧版Windows PowerShell中把视频/图片二进制直接用`>`转储，它可能按文本处理而破坏文件。图片流、AAC封装、PCM都由Node以Buffer接收。

## 第四步：先保存混音，再分离音乐主体

提取原始AAC音轨的等价FFmpeg参数如下。实际脚本通过stdout保存，保留了原编码内容。

```text
ffmpeg -i 输入.mp4 -map 0:a:0 -vn -c:a copy
  -movflags frag_keyframe+delay_moov+default_base_moof -f mp4 pipe:1
```

`-vn`是不输出视频，`-c:a copy`是不重新压缩音频，`-map 0:a:0`选第一条音频轨。`delay_moov`用于处理AAC开头的预滚动与时间信息。曾发现`empty_moov`方案会影响开头解码信息，因此没有把“编码流一致”和“PCM长度完全一致”混称。

20条输出都核对了AAC ADTS编码内容哈希。容器时长、可听PCM长度与预滚动可能略有差异，完整字段在`mixed-index.json`；声画比较使用原视频解码的音频时间，不依赖重新封装音频的容器时长猜切点。

音乐主体分离使用独立本地Python环境、audio-separator和UVR_MDXNET_KARA_2模型，CPU执行。短样成功后才跑全量，每条缓存结果以便失败续跑。遇到MSVC运行库加载问题时，只给当前Python进程增加已存在DLL目录；没有全局修改系统配置。工具与具体模型出处见音频处理说明。

模型把“人声”和“非人声”分开，并不能可靠把音乐与所有电影音效分开。因此名称是“音乐主体候选”。统一`music-index.json`用相对路径标明原混音、候选、状态与哈希。

## 第五步：分析声音，再对照视觉事件

本地HyperFrames信号分析提供谱通量起音、拍点候选与速度候选；辅助脚本计算RMS能量和自相关。RMS是音量强弱，起音是声音突然变化，拍点是周期模型推断，三者不同。

`build-study.mjs`把人工标记的视觉事件与最近声音起音、模型拍点对齐，保存正负毫秒差。V01–V10未提供结构化原帧事件的部分使用机器变化候选并明确标注，不伪装成人工切点。

```powershell
node .\scripts\build-study.mjs
```

这个脚本合并报告与数据，生成学习页数据、覆盖统计和声画候选对照。正时间差意味着视觉晚于声音；接近零并不自动证明剪辑好看。先定位复听，再决定是否调整。

## 第六步：把FastX方案落到可编辑数据

真实源片是3840×1600、24000/1001fps、10bit PQ/BT.2020。提取候选图时经过HDR→SDR映射，不把发灰预览当电影原有调色。30张新候选图只证明那个时间点的构图；不能据此编造前后4秒都可用。

两分钟方案采用明确设计的128BPM、4/4拍、64小节、256拍，共120秒。24fps时间线的拍点量化误差写在CSV中，不把它当参考歌曲测得的BPM。

```powershell
node .\scripts\build-fastx-rhythm-guide.mjs
```

脚本生成原创合成节奏导轨、可编辑MIDI和拍点CSV。它帮助摆镜头，不是最终商业配乐。这次交付的是两分钟剪辑设计和资源，不宣称已经渲染两分钟电影；实际完成并能看的影片仍是V05小样。

## 第七步：检查、打包、公开

检查项目包括：JSON可读、20个ID齐全、证据路径存在、原帧连续、脚本语法、音轨完整解码、源编码内容一致、MIDI时长、网页播放与单帧读取、ZIP内容、Git文件清单。没有把未经试听的音乐标作听感合格。

Git流程在已有仓库副本进行，先`git status`与`git fetch`确认状态，再有选择地复制研究资料。原始本地路径、环境变量、模型缓存和整部电影不纳入提交；音乐和可编辑工程通过Release下载包提供。

```powershell

git diff --stat
git add README.md studies projects

git push origin main
gh release create reference-library-2026-11-05 --title '20条混剪原生帧学习库与可编辑工程' --notes-file release-notes.md
```

以上为流程说明，实际本轮文件列表、验证结果与发布地址看最终验证报告及仓库提交记录。`git push`上传版本历史；Release附件用于较大的可下载媒体包，不把每次音乐导出都塞进Git历史。
